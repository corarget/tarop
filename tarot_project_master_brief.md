# 🔮 Таро-проект — единый рабочий бриф

**Актуальность:** 19 ноября 2026 года  
**Источник:** решения, идеи и результаты исследований, обсуждённые в текущем чате  
**Статус:** предпроектная подготовка; реальный продукт ещё не разработан и не запущен  
**Назначение документа:** самостоятельный контекст для нового чата/проекта, дальнейшей разработки и проверки бизнес-гипотез.

> **Как читать:** «Согласовано» означает прямое пожелание пользователя; «Рекомендуется» — предложение ассистента, не обязательно принятое; «Гипотеза» — не подтверждено практикой; «Блокер» — препятствие, которое нужно разрешить до соответствующего этапа. Рыночные цифры из предыдущего исследования местами взяты из открытых заявлений компаний и продавцов сайтов/ботов: это не независимый аудит. Перед принятием финансовых или юридических решений данные перепроверять.

## 1. Цель, условия и амбиции

### Согласовано

- Построить **русскоязычный коммерческий сервис таро-раскладов** с упором на аудиторию **СНГ**, прежде всего Беларусь и Россия.
- **Основной канал обслуживания — Telegram-бот**, дополнительно **сайт**. В идеале консультации доступны и там, и там с общей историей.
- Продукт подаётся как сервис **персонализированных таро-консультаций** с выбором нескольких тарологинь: у каждой профиль с фотографией/визуалом, описанием, характером и стилем общения.
- **Расклады и ответы генерирует ИИ**, а не штат реальных экспертов. Клиент задаёт свободный вопрос, получает трактовку карт и может общаться дальше.
- Пользователь считает предпочтительным **позиционирование консультанток как настоящих людей** с нераскрытым использованием ИИ. Ассистент возражал против выдуманных реальных биографий и скрытого введения в заблуждение; рекомендуемая для реализации альтернатива — узнаваемые **виртуальные персонажи** с прозрачным описанием AI-формата. **Разногласие по прозрачности не разрешено**, не считать его согласованным.
- Пользователь хочет **максимально самостоятельно вайбкодить**, но ожидает, что **ассистент подготовит и напишет код**, а он будет **проверять и развёртывать**.
- Ресурс времени: **5–10 часов в неделю**.
- Денежный бюджет на первые тесты: **$10–20**. Платная реклама на старте не планируется.
- Доход **$100 в месяц — минимальный показатель начальной жизнеспособности**, **не** долгосрочная бизнес-цель. При успехе интересен масштаб **$500–1 500, затем $2 000–5 000+ в месяц**, но без обещаний, что эти цифры достижимы.
- Место получения дохода: **Беларусь**. Пользователь не хочет оформлять деятельность на раннем этапе, предпочёл бы получать **USDT**; при этом покупателю нужна **максимально простая оплата обычной картой, без настройки криптокошелька**.
- Пользователь просит не ставить юридические вопросы во главу планирования, но **учитывать риски**. Разработка не должна включать инструменты сокрытия доходов, обхода обязательных платформенных правил или поддельные подтверждения личности.

### Не определено окончательно

- Название и айдентика бренда.
- Кто будет основной «медийной» консультанткой, сколько персонажей останется на платном запуске.
- Конкретные тарифы и валюта представления цен каждому рынку.
- Законный и технически доступный маршрут получения выручки при заданных условиях: **пока блокер**.
- Идентификаторы бота, аккаунты соцсетей, репозиторий, домен, API-ключи.
- Наличие/доступность сервиса генерации изображений и внешней LLM API под бюджет.

## 2. Основной продукт и пользовательские сценарии

### Желаемое позиционирование

Сервис персональных таро-разборов, эмоциональных интерпретаций и продолжения разговора. **Сила не в факте генерации текста ИИ**, а в качественном опыте: персонаж, атмосфера, конкретный вопрос, связный расклад, объяснение карт, память и возвращение в чат. Таро не имеет научной доказанности как способ предсказывать будущее; поэтому нельзя представлять ответы как гарантии фактов, диагнозы или финансовые прогнозы.

### MVP для клиента

1. Пользователь нажимает `/start` в Telegram.
2. Видит вводное сообщение, каталог **2–3 персонажей** и понятный выбор тем (отношения, бывшие, решения, работа, свой вопрос).
3. Выбирает персонажа; задаёт вопрос в свободной форме.
4. Если без уточнения нельзя сделать связный ответ, бот задаёт **не больше одного** вопроса.
5. Backend **случайным образом** выбирает карты из собственной базы колоды (а не даёт модели произвольно «подтасовывать» карты). Опционально прямое/перевёрнутое положение.
6. Модель получает вопрос, выбранные карты, значения, ограниченный контекст диалога и стиль персонажа.
7. Пользователь получает **карты → разбор каждой → общий смысл → аккуратный вывод**. Ответ визуально оформлен несколькими сообщениями/блоками, а не «простынёй».
8. Разрешается уточняющий вопрос в рамках консультации; история привязана к пользователю.
9. Для платной версии появляется предложение купить новый/углублённый расклад с заранее известной стоимостью и границами услуги.
10. В перспективе можно перенести или продолжить сессию на сайте после безопасной авторизации.

### Механика общения

- Пользователь склоняется к **диалогу с консультанткой**, а не к обезличенному единоразовому генератору.
- Лучше продавать **законченную консультацию с ограниченным количеством уточнений**, чем бесконечную оплату каждого сообщения. Сторонняя манипуляция тревогой ради допродаж недопустима.
- Персонажи должны различаться **манерой речи, степенью прямоты, способом объяснять неопределённость и характером выводов**, а не только аватаром.
- **Персонаж №1** (пример: Мира) — тёплые разборы отношений; **№2** (пример: Алиса) — прямые, прагматичные трактовки решений; **№3** (пример: Ева) — вдумчивые темы жизненных перемен. Имена — рабочие, окончательно не утверждены.
- Для продвижения возможен **один основной образ**, остальные — как альтернативы внутри продукта.
- Нужна возможность пользователю **удалить историю**; личные истории и чувствительные сведения не использовать в публичном контенте без разрешения.

### Что не делать в первом MVP

- 10+ консультанток и сложный маркетплейс;
- видеозвонки, голосовые сообщения, обширные подписки и loyalty-система;
- сложная админка, SEO-портал на сотни статей, автопостинг в разные соцсети;
- глубокая синхронизация всех платформ до первой проверки продуктового спроса;
- недели доработок анимаций и декоративного UI вместо работающего сценария.

## 3. Целевая аудитория и ценностное предложение

**Основная гипотеза сегмента:** совершеннолетние русскоязычные пользователи, особенно заинтересованные в отношениях, расставаниях, неоднозначных романтических ситуациях, сложных выборах, самоанализе. Первой нишей для контента предлагаются **отношения**, поскольку это эмоционально насыщенная, понятная тематика; внутри сервиса оставить и другие темы.

**Основное обещание продукта:** красивый и персональный таро-разбор на свой вопрос за несколько минут, возможность уточнения и возвращения к истории. Не обещать объективных предсказаний, гарантированного возвращения партнёра и других неподтверждаемых результатов.

**Дифференциация по сравнению с дешёвыми AI-ботами:** сочетание узнаваемых персонажей, последовательной переписки, контекста, аккуратного UX и контентной воронки в соцсетях. Только «несколько тарологов» как фича уже есть у конкурентов (например, TaroGPT), этого недостаточно.

## 5. Маркетинг: главный шанс получить трафик без бюджета

### Каналы (рекомендуемый порядок тестирования)

1. **VK Клипы** — важный канал для аудитории России.
2. **TikTok** — перспективен для слайд-шоу и каруселей, но доступность нового контента в РФ ограничена; нельзя делать его единственной опорой.
3. **Instagram Reels** — переиспользование форматов; для РФ есть платформенные ограничения доступа.
4. **YouTube Shorts** — дополнительное распространение, с учётом неудобства кликабельных ссылок в коротких видео.
5. **Telegram-канал/бот** — удержание, бесплатный опыт, предложения, рефералы.
6. **Позже:** SEO-страницы карт/тем, каталог ботов, микроинфлюенсеры, партнёрские публикации и реферальная программа.

### Ключевая идея пользователя: карусели-переписки

**Приоритетная ставка** — короткие драматизированные истории в виде **скриншотоподобной переписки клиента и тарологини**, оформленные как 5–8 слайдов. Часто на темы отношений, бывших, измен, неожиданного решения, сложного выбора. Зритель пролистывает историю, получая интригу → расклад → развязку → органичный CTA к собственному разбору.

**Важно:** постановочные диалоги обозначать как вымышленные сценарии, а не выдавать за подтверждённые клиентские отзывы. Реальные обращения публиковать только с согласия и после обезличивания.

#### Форматы и стартовое распределение

- **~40–50%** — карусели с переписками и историями;
- **~25–30%** — «выбери одну из трёх карт»;
- **~20–25%** — разборы жизненных ситуаций;
- **~10%** — объяснения карт, символики и экспериментальные форматы.

**Примеры завязок:**
- «Он написал спустя 6 месяцев молчания…»
- «Я узнала, что у него есть девушка, но он продолжает со мной общаться».
- «Мы дружили семь лет. Вчера он меня поцеловал…»
- «Мне предложили переехать, и я боюсь всё потерять».
- «Я пришла узнать, вернётся ли он. После расклада поняла, что уже не хочу».

**Рекомендация:** сериализовать сюжеты с узнаваемой главной героиней-консультанткой. В качестве контентной концепции использовать один аккаунт бренда, не разбрасываться на 5 аккаунтов и 5 персонажей с нуля.

### Внутренний генератор контента — отдельное преимущество для создателя

В административной панели в перспективе должна быть форма:
- тип («переписка», «выбери карту», «мини-история»);
- тематика;
- выбранный персонаж;
- тональность;
- количество слайдов (4–10);
- генерация сценария, **ручная правка каждого слайда**;
- экспорт слайдов в PNG 1080×1920, позднее видео;
- название публикации, CTA, метка источника, дата и результаты.

**Принцип:** создание **одной** качественной истории в несколько кликов, а не бесконтрольная массовая генерация спама. На первой неделе контент-студию не делать полноценной: достаточно сценария и одного простого визуального шаблона.

### Ещё идеи бесплатного роста

- Красивые **шаринговые карточки** результата расклада, без публикации личного вопроса.
- Реферал «пригласи друга → бесплатный мини-расклад» (проверить злоупотребления).
- Коллаборации с микроавторами и тематическими Telegram-каналами.
- «Карта дня» как повод вернуться (позже, с возможностью отключить уведомления).
- SEO-страницы «таро на отношения», «значение карты», «расклад на ситуацию» (долгосрочная ставка, не первая неделя).

### Атрибуция трафика

Отдельные deep links Telegram вида `https://t.me/<bot>?start=<source_code>` для каждого канала/кампании. В базе хранить `first_source`, `last_source`, `campaign_id` и события переходов. Не собирать лишние персональные данные. Источник при первом запуске не должен перезаписываться последующим переходом.

|---|---:|
| Первое знакомство/мини-расклад | Бесплатно |
| Короткий индивидуальный ответ | **59–99 ₽** |
| Подробный разбор | **149–249 ₽** |
| Расширенная консультация + уточнения | **349–499 ₽** |

В раннем обсуждении фигурировали **9 / 19 / 35 BYN**, но после исследования конкурентов эти уровни признаны завышенными для базового автоматического расклада. Тарифы нужно A/B-тестировать и сопоставлять **цену клиенту** с **фактическим доходом после комиссий**.

### Платежи: текущая реальность и блокеры

- Пользователь планирует принимать доход через Беларусь, не хочет оформлять деятельность на старте и предпочёл бы **USDT**; покупателям нужна оплата картой без возни с криптой.
- **Telegram требует Stars для цифровых товаров/услуг, продаваемых прямо внутри ботов и Mini Apps.** Нельзя закладывать обход этого требования переадресацией из Telegram для оплаты того же цифрового продукта.
- Доход от Stars возможно выводить по условиям Telegram через **Fragment**, вознаграждение номинируется в TON (не напрямую USDT). В обсуждении упоминались эквивалент **$0,013 за 1 Star** и возможный срок удержания до 21 дня, минимальный порог вывода; всё необходимо повторно проверить перед запуском.
- Для оплаты на **внешнем сайте** рассматривались белорусские сервисы **WEBPAY** (https://webpay.by/cards/), **bePaid** (https://bepaid.by/cards), **«Хуткі Грош»** (https://hutkigrosh.by/erip/internet-ekvajring). Это кандидаты при соответствующей регистрации/проверке, а не гарантированно доступные пользователю решения.
- Схема **карта → USDT продавцу** без полноценного оформления и проверки **не подтверждена**; рассчитывать на неё как на готовое решение нельзя. Не направлять покупателей в ручные P2P-операции или непроверенные агрегаторы под видом простого эквайринга.
- До подтверждения маршрута продаж: **тестовая среда Stars, бесплатная бета, измерение намерения купить**. Не выдавать режим «оплата ожидается» за реальную обработку платежа.
- Юридические и налоговые условия Беларуси, в т.ч. ограничения рекламы эзотерических услуг, сохраняются как риск. Пользователь хочет уделять им минимум внимания, но это **не отменяет существование требований**. Сервис не должен включать сокрытие реальных платежей.

### Модель экономики

Главные метрики — не только стоимость генерации, а:

- CAC (стоимость нового платящего клиента; на бесплатном маркетинге считать хотя бы затраченное время);
- конверсия просмотр → переход → запуск → завершённый бесплатный расклад → оплата;
- AOV (средний оплаченный заказ);
- повторные платежи на покупателя;
- LTV за 30/60/90 дней;
- фактически полученный доход после платформенных комиссий/возвратов;
- стоимость AI-генерации на законченный заказ и себестоимость поддержки.

**Иллюстративный сценарий:** при $3 фактического дохода на заказ до расходов — ~34 заказа для $100, ~334 для $1 000, ~667 для $2 000, ~1 667 для $5 000. Это **арифметические ориентиры, не прогноз** и не доказательство соответствующей конверсии.

### Финансовые контрольные уровни

1. **$100–300/мес:** доказали, что пользователи готовы регулярно платить.
2. **$500–1 500/мес:** воспроизводимый канал привлечения и повторные заказы.
3. **$2 000–5 000+/мес:** оптимизация воронки, качественное удержание, расширение контента/SEO, надёжная платёжная и операционная схема.

Успех измерять **чистой экономикой**, а не показными просмотрами или суммой «возможной выручки».

## 7. Предлагаемая архитектура

### Стек

- **Язык:** TypeScript.
- **Backend:** Cloudflare Workers (Telegram webhook + HTTP API + бизнес-логика).
- **База:** Cloudflare D1 / SQLite.
- **Telegram:** Bot API, webhook с проверкой секретного токена; обработка команд, inline-кнопки, сообщения.
- **Сайт:** React + Vite на Cloudflare Pages/Workers Assets (или даже статическая витрина на первой неделе).
- **Генерация:** внешний LLM API (не привязываться к одному поставщику) с жёсткими лимитами токенов и стоимости; для первого теста рассмотреть бесплатные квоты Cloudflare Workers AI, но качество проверить. В предыдущем обсуждении рассматривалась GPT-5.4 mini; цены могут меняться.
- **Контент:** шаблон слайдов в HTML/CSS, экспорт PNG (позже автоматизация и редактор).
- **Аналитика:** свои события в D1, без дорогих SaaS.

### Логическая схема

```text
Telegram Bot API ─┐
                  ├─> Cloudflare Worker API ──> D1 (users/personas/readings/messages/events)
Web / Mini-site ──┘             │
                                ├─> tarot engine: random cards + canonical meanings
                                ├─> LLM adapter: answer generation
                                └─> payment adapter: initially disabled/test-only
```

**Не создавать два отдельных backend'а для сайта и бота.** Общие пользователи и история — единая модель. Для веб-кабинета позже понадобится отдельная безопасная схема входа и привязки Telegram-аккаунта.

### Минимальные сущности данных

```text
users: id, telegram_id, created_at, first_source, last_source, locale, preferences
personas: id, name, short_bio, tone_prompt, portrait_path, active
cards: id, name_ru, arcana, upright_meaning, reversed_meaning, image_path
readings: id, user_id, persona_id, question, topic, status, cards_json, result_text, created_at
messages: id, reading_id, role, content, created_at
usage_limits: user_id, free_readings_used, updated_at
analytics_events: id, user_id?, event, properties_json, created_at
payments (later): id, user_id, reading_id?, provider, status, amount, currency, provider_event_id
```

### Обязательная техническая гигиена

- AI/API-ключи только в секретах окружения, **не** в git/frontend.
- Проверка Telegram webhook token, фильтрация событий, идемпотентность обновлений (Telegram иногда повторяет доставку).
- Rate limiting на пользователя, глобальные лимиты генерации и дневной бюджет.
- Не повторять платное списание при ошибке повторной отправки.
- Сохранять выбранные карты и результат в базе до подтверждения успешной доставки.
- Сценарии таймаута API, отсутствия контекста, прерывания сессии.
- Минимизация хранения личных историй, команда удаления истории и политика доступа к админке.
- Структура кода по модулям, не «один огромный файл».

### Рекомендуемые модули

`telegram/`, `api/`, `db/`, `personas/`, `tarot/`, `llm/`, `analytics/`, `payments/` (пока интерфейс и моки), `content/` (после первого работающего бота).

## 8. План на 30 дней из беседы — скорректированный на 5–10 ч/неделю

**Важно:** предыдущий 30-дневный план был достаточно плотным и не вполне соответствовал ограничению 5–10 ч/неделю. Приоритет — уменьшить MVP, проверять спрос поэтапно и не обещать полный сайт+бот+генератор контента+оплаты за месяц.

| Период | Приоритет | Критерий завершения |
|---|---|---|
| **Неделя 1** | Простой Telegram-бот, одно сквозное демо, проверка генерации | `/start` → выбор темы → вопрос → случайные карты → адекватный ответ; тестовая работа с 5–10 людьми |
| **Неделя 2** | D1, ограничение бесплатных раскладов, историю, персонажей, логирование ошибок | Работа без участия владельца; стабильные ответы, базовая аналитика |
| **Неделя 3** | Контент: 6–12 каруселей, аккаунты, источники трафика; простой сайт-витрина | Первые реальные переходы в Telegram с отслеживанием источников |
| **Неделя 4** | Улучшение UX, платежи **только если реальный канал подтверждён**, ещё контент | Данные по конверсии, качество и интерес к платному предложению; решение о следующем месяце |

**Условие перехода к масштабированию:** реально приходят пользователи, значимая часть заканчивает бесплатный расклад, есть повторные обращения и подтверждение интереса к платной услуге. Не строить сложные функции ради календарного плана.

### Контрольные показатели (гипотезы)

- Первая бета: 5–10 добровольцев, 15 тестовых ситуаций; минимум 12/15 ответов без существенных ошибок.
- Конверсия запуск → законченный первый расклад: ориентир 60%+, затем фактические данные.
- Первый контентный тест: 12–24 публикации **после** запуска работающего бота.
- Переходы и привлечённые пользователи важнее охватов.
- Нажатия на платный тариф без реальной оплаты считать **интересом**, не выручкой.

## 9. Техническое задание на первую неделю (под текущие ограничения)

**Цель недели:** бесплатный прототип Telegram-бота с **одним действительно работающим end-to-end сценарием**, развёрнутый пользователем по инструкции ассистента. **Не** реализовывать платёжную систему, сайт с авторизацией и полноценную админку.

### Минимальный пользовательский сценарий

```text
/start
  ↓
«Добро пожаловать» + кнопка «Попробовать бесплатный расклад»
  ↓
Выбор темы: Отношения / Работа / Свой вопрос
  ↓
Пользователь текстом описывает ситуацию
  ↓
Бот выдаёт три случайные карты из подготовленной колоды
  ↓
LLM генерирует осмысленный разбор:
  - карта 1 и её значение в ситуации
  - карта 2 и её значение
  - карта 3 и её значение
  - общий вывод без категоричного предсказания
  ↓
Кнопки: «Задать уточнение» / «Новый расклад»
```

### Scope первой итерации

**Должно быть:**

- Код TypeScript-проекта Cloudflare Worker с Telegram webhook.
- Модуль Telegram-обработчиков и безопасная конфигурация окружения.
- Внутренняя база колоды: для прототипа можно использовать **22 Старших аркана** с корректными названиями и краткими значениями. Полную колоду 78 карт добавить позже; выбор обязательно программный.
- Один персонаж (Мира как рабочее имя) и один стиль ответов; инфраструктура, допускающая добавление других персонажей без переписывания кода.
- Одно временное хранилище состояния / желательно D1, если укладывается в объём первой недели.
- Лимит **1 бесплатный завершённый расклад на Telegram ID** для публичной беты; тестовый whitelist для разработчика.
- Базовая обработка ошибок AI API, повторных webhook, неверного ввода.
- README: локальная установка, создание бота BotFather, `wrangler` конфигурация, секреты, миграции, деплой, настройка webhook и тесты.
- Простой тестовый набор из 10–15 вопросов и критериев качества.

**Не должно быть в первой неделе:**

- Реальной оплаты, USDT/Stars/эквайринга;
- полноценного веб-чата и синхронизации каналов;
- сложных ролей/регистрации/подписок;
- конструкторов контента, массового автопостинга, SEO;
- сложной анимации карт, голосов, десятков персонажей.

### Примерные трудозатраты владельца (5–10 часов)

| Действие | Время владельца |
|---|---:|
| Создать Telegram-бота и выдать необходимые несекретные настройки | 20–30 мин |
| Создать/настроить Cloudflare и развернуть код по README | 1–2 ч |
| Протестировать 10–15 разных вопросов, отметить ошибки | 1,5–2,5 ч |
| Уточнить стиль ответов и сценарии | 1–2 ч |
| Пригласить 5–10 бета-тестеров и собрать отзывы | 1–2 ч |
| Резерв на исправления | до 1 ч |

**Роль ассистента:** подготовить весь код, файловую структуру, SQL/миграции, промпты, инструкции, набор тестов; после пользовательского деплоя исправлять ошибки по логам и обратной связи. **Не обещать фонового выполнения**; реализация делается в активных задачах/ходах чата.

### Критерии приёмки

- `/start` открывает понятное меню.
- Ответ клиента с вопросом не теряется между обновлениями webhook.
- Выбранные карты фиксируются и соответствуют тексту интерпретации.
- Нет утечек API-ключей в ответах, клиентском коде, Git.
- Бот обрабатывает повторные события и API-ошибки без повторных платных генераций.
- Первый расклад выдаётся за приемлемое время; при задержке виден статус.
- Бесплатный лимит и тестовые исключения работают предсказуемо.
- Владельцу хватает README для повторного развёртывания без ручного «магического» исправления конфигурации.

### Первый следующий запрос к ассистенту (готовый промпт)

> Начинаем разработку таро Telegram MVP по брифу. Сгенерируй полностью готовый к деплою TypeScript-проект на Cloudflare Workers для Telegram Bot API: `/start`, выбор темы, приём свободного вопроса, случайный выбор 3 карт из 22 Старших арканов, интерпретация через LLM-провайдер с конфигурацией из секретов, надёжная обработка webhook, минимальная D1-схема, ограничение бесплатного расклада, тесты и подробный README для самостоятельного развёртывания. Не добавляй реальную оплату и веб-чат на этом этапе. Перед публикацией проекта проверь сборку и тесты. Уложись в минимально возможные затраты.
